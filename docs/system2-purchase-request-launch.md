# خطة إطلاق موديل طلبات الشراء — النظام الأساسي

## النطاق المعتمد

هذا الإصدار يخص `requests.html` داخل نظام المشتريات الأساسي. لا يغيّر بوابة الطلبات والموافقات المنفصلة (النظام 3).

دورة الطلب المعتمدة:

1. ينشئ موظف الصيانة والتشغيل الطلب من مشروع موجود في سجل المشاريع المعتمد.
2. يعتمد مدير الصيانة والتشغيل الحاجة أو يعيد الطلب أو يرفضه.
3. يأذن مدير المشتريات ببدء التسعير أو يعيد الطلب أو يرفضه.
4. تتابع المشتريات التسعير والمناقشات والمستندات داخل ملف الطلب.
5. يمكن ربط الطلب بعدة أوامر شراء، ويمكن لأمر الشراء الواحد تجميع عدة طلبات، مع توزيع الكمية على مستوى البند.

## ترتيب الإطلاق

1. خذ نسخة احتياطية قابلة للاستعادة من قاعدة الإنتاج قبل التغيير.
2. طبّق الملفات السابقة بالترتيب المدون أعلى ملف الهجرة إذا لم تكن مطبقة، ثم طبّق:

   ```text
   db/system2-purchase-request-workspace.sql
   ```

   الملف داخل معاملة واحدة، لذلك يفشل كاملًا إذا تعذّر أي جزء منه.

3. حدّث مخزن PostgREST بعد الهجرة إن لم يلتقط الدوال والأعمدة تلقائيًا:

   ```sql
   notify pgrst, 'reload schema';
   ```

4. تأكد من وجود ربط Cloudflare R2 باسم `SUPPLIER_DOCS`، ومن أسرار `SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` و`RESEND_API_KEY` المستخدمة أصلًا في المشروع.
5. انشر نسخة Preview من الفرع وشغّل مصفوفة القبول أدناه بحسابات اختبار مستقلة.
6. انشر قاعدة البيانات أولًا ثم ملفات Pages. لا تنشر الواجهة الجديدة قبل الهجرة لأن الواجهة تقرأ جداول الصلاحيات والربط والمرفقات الجديدة.

## تهيئة الصلاحيات

تنشئ الهجرة خمسة ملفات جاهزة:

| الملف | الاستخدام |
|---|---|
| `requester` | موظف الصيانة أو التشغيل الذي ينشئ ويتابع طلباته |
| `maintenance_manager` | مدير الصيانة والتشغيل واعتماد الحاجة |
| `procurement_officer` | التسعير والمتابعة وربط أوامر الشراء |
| `procurement_manager` | إذن بدء التسعير وإدارة التنفيذ |
| `module_admin` | إدارة مستخدمي الموديل وصلاحياته وإعداداته |

تمنح الهجرة مديري النظام الحاليين ملف `module_admin` تلقائيًا لتجنب قفل لوحة الإدارة. بعد النشر، استخدم شاشة مستخدمي الموديل لإرسال دعوات شخصية وتحديد الإدارة وملف الصلاحيات. يضبط المدعو كلمة مروره بنفسه، ولا تُرسل كلمة مرور في البريد.

ملف `module_admin` يدير موديل طلبات الشراء فقط ولا يحوّل صاحبه إلى مدير للنظام الأساسي. إنشاء حساب بدور مدير النظام أو تعديل مدير نظام قائم محصور بمدير نظام قائم. كما لا يستطيع مدير ذو صلاحية أدنى تعديل مدير موديل أو منح نفسه صلاحية إدارة المستخدمين.

لا تُسنِد مدير صيانة لإدارة قبل التأكد أن `proc_departments.manager_user` يشير إلى حساب نشط يحمل `maintenance_manager`. ولا تعتمد بوابة التسعير قبل وجود حساب نشط يحمل `procurement_manager`.

## فحوص ما قبل فتح الاستخدام

نفّذ الاستعلامات التالية للقراءة فقط:

```sql
select profile_key, name_ar, active
from proc_pr_permission_profiles
order by sort_order;

select d.id, d.name_ar, d.manager_user, u.active, u.pr_profile_key
from proc_departments d
left join proc_users u on lower(u.username)=lower(d.manager_user)
where d.active
order by d.name_ar;

select u.username, u.display_name, u.pr_profile_key, u.department_id, u.pr_department_ids
from proc_users u
where u.active
order by u.pr_profile_key, u.username;

select value
from proc_settings
where key='projects_registry';
```

يجب أن تكون نتيجة كل إدارة نشطة مرتبطة بمدير صالح، وأن يحتوي سجل المشاريع على الأسماء التي سيختارها الموظفون حرفيًا.

## مصفوفة القبول

استخدم طلب اختبار واحد على الأقل ونفّذ ما يلي:

- مقدّم الطلب: يحفظ مسودة، يعدّلها، يرسلها، ويرى طلباته فقط.
- مدير الصيانة: يرى طلب الإدارة، يعتمد الحاجة، ويختبر الإرجاع مع سبب.
- مدير المشتريات: لا يقرر قبل بوابته، ثم يأذن ببدء التسعير.
- موظف المشتريات: يضيف مناقشة ومستندًا، ويربط أمرين بطلب واحد.
- تجميع الطلبات: يربط أمر شراء واحد بطلبين مختلفين.
- التوزيع: يعدّل توزيع رابط قائم ويتأكد من عدم مضاعفة الكمية، ثم يحاول تجاوز الكمية ويتأكد من الرفض.
- المبالغ: يتأكد حساب بلا `pr_view_financials` من ظهور الإخفاء، ويتأكد الحساب المخول من القيمة.
- المستندات: يرفع PDF أو JPG أو PNG، يفتحه من تبويب المستندات، ويتأكد من ظهور الحدث في السجل.
- الدعوة: يرسل دعوة Resend، يضبط الموظف كلمة مروره، ثم يدخل بالإدارة وملف الصلاحيات الموقعين في الدعوة.
- الطباعة: يطبع تقرير الطلب ويتأكد من البنود ونسبة التغطية والحالة.

## المراقبة بعد الإطلاق

راقب أخطاء Cloudflare Functions لمساري `/api/pr-doc` و`/api/staff-invite`، وأخطاء PostgREST للدوال `pr_save_request` و`pr_decide` و`pr_link_purchase_order`. راجع يوميًا في أول أسبوع الطلبات المتوقفة عند `maintenance_review` أو `procurement_review`، والطلبات ذات `current_owner` فارغ.

```sql
select id, workflow_state, current_owner, updated_at
from proc_purchase_requests
where workflow_state in ('maintenance_review','procurement_review')
  and current_owner is null;
```

## الرجوع الآمن

عند ظهور مشكلة، أعد نشر آخر نسخة مستقرة من Pages وأوقف دخول المستخدمين إلى `requests.html` مؤقتًا. لا تحذف جداول الربط أو الإصدارات أو المرفقات؛ فهي سجلات تشغيلية. الهجرة إضافية وتبقي `po_number` و`doc_key` وحقول Supabase القديمة للقراءة، لذلك يمكن للواجهة السابقة العمل أثناء معالجة السبب. أصلح السبب في هجرة لاحقة ثم أعد فتح الموديل.
